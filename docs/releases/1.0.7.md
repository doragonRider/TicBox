# TicBox 1.0.7

手机 App、手表 Local Bridge 和内置的 Magisk 模块统一为 1.0.7（versionCode 8）。

## 改进

开着变更日志时，每读一次日志都要启动一次 root 辅助进程，每次约 2 秒（su 约 0.05 秒，虚拟机启动约 0.8 秒，其余是辅助进程里的核对和查询），一次增量同步要启动三四次。这一版：

- **健康库的日志改由进程内模块读取。** 读取在官方健康应用的进程里完成，不再启动辅助进程。
  - 普通应用连不上另一个应用的 Unix socket，所以模块通过 Binder 提供只读查询。
  - 交接凭一个随机令牌：模块每次启动时生成，写在官方应用的私有目录里，只有 root 能读到。
  - 所有校验仍在 Local Bridge 里，用原来的代码完成。算出的文件代际和辅助进程相同，所以换成模块读取后不会重建基线。
  - 256 KiB 以内的回复直接放在 Binder 回复里，更大的经只读共享内存传递，一次最多 4 MiB，所以大行也不必退回辅助进程。
  - 没装模块，或者模块读取出错时，照旧用辅助进程。
- **每个来源每次同步只读一次日志。** 日志窗口、各张表的新事件和对应的行一次带回，不再先读窗口、再每张表各读一页。每页最多 128 个事件，原来是 32 个。
- **运动库没变化时不启动辅助进程。** 先用 su 和 stat 看运动库的修改时间和大小，和上次一样就沿用上次的日志窗口。这样平时只有训练之后的那次同步需要启动辅助进程。
- **辅助进程里的 schema 校验只做一次。** 原来算文件指纹时又校验了一遍。
- **一页的行太多、放不下时，** 减少这一页的事件数再读，不再报错后退回完整扫描。

## 修复

- **一条超大的健康记录不再卡住整张表。** 一行的 JSON 接近 1 MiB 时，一帧放不下，原来这张表每次同步都停在这一行，后面的记录都发不出去。1.0.6 起这一行还会先排进队列，组批时才报 `row_exceeds_budget`。现在一行超过 960 KiB 时，读取时就去掉它最大的单元格，直到放得下，并在行里用 `oversizedColumns` 标出去掉了哪些列。
  - 这样的行只发一次，不会每次同步重发，也不会让这次扫描算作不完整。
  - 手机把它记为部分源行；之前已经完整收到过的单元格，保留原来的值。
  - 1.0.6 已经排进队列的超大行，组批时同样处理，卡住的表在更新后就能继续同步。
  - 整行超过约 2 MB、连 CursorWindow 都装不下的行，原来一读就失败（`query_failed`），同样卡住整张表。现在它之前的行照常发出，它自己先量出各单元格的大小，再不带最大的那些重读一次，大单元格本身从不读出。健康库、运动库和变更日志的读取都这样处理；SESSION 的新增列超过 960 KiB 时，在查询里就略过。
  - 没开 root 时运动记录走官方运动 Provider，它会改写查询条件，这里没有这样处理，超过约 2 MB 的运动记录仍会让那张表停住。
- **一页读取的内存有了上限。** 1.0.6 起日常同步每页读最多 1024 行，且不再按大小截断，大行多时会占用很多内存。现在一页最多保留约 4M 字符的行内容，超出就提前结束这一页，平常的页远远到不了这个上限。

## 诊断

手表日志新增几条，读取方法见[健康数据 · 排查](../dev/health.md#6-排查)：

- `Journal read through the module`：查询次数和耗时；
- `Journal helper finished`：辅助进程的操作和耗时；
- `Journal window unchanged`：运动库没变，沿用了上次的窗口；
- `Health module journal not available` 和 `Journal read through the module failed`：模块那条路没走通，改用了辅助进程；
- `Source row too large to deliver whole` 和 `Source row too large for a cursor`：某行太大，去掉了最大的单元格，带表名和去掉的单元格数。

## 升级

1. 用 ADB 安装新的手机 APK：`adb install -r ticbox-phone-1.0.7-release-<commit>.apk`，数据保留。
2. 在本地桥接页更新手表上的 Local Bridge。
3. 在模块页更新 Magisk 模块，按提示重启手表。新模块要等官方健康应用重新启动后才生效。

只更新 Local Bridge 时，健康日志仍由辅助进程读取，但每次同步只读一次日志、运动库没变化时跳过这两项照样生效。

## 未在真机验证

- 手表上的 Local Bridge 能否拿到模块交回的 Binder 并调用它。“普通应用连不上另一个应用的 socket”也是按 Android 默认的 SELinux 策略推断的，没在手表上试过。
- 模块和辅助进程算出的文件代际是否一致。不一致时，第一次经模块读取的同步会重建一次基线，之后恢复正常。
- 一次增量同步实际省下多少时间。
