# TicBox 1.0.10

手机 App、手表 Local Bridge 和内置的 Magisk 模块统一为 1.0.10（versionCode 11）。

## 修复

- **手表的读取和组批真正同时进行。** 1.0.9 在真机上的全量同步从约 23.4 秒降到 18.7 秒，但几乎都来自运动库只启动一次辅助进程；data_point 仍是每页约 0.65 秒，和 1.0.7 一样，手表日志里也没有一次提前组好的批次（`Packed ahead`）。原因是预读只比已组好的批次多读一页，读完要等回复写出才接着读；手机提前发出的请求在这一页读完之前就到了，只好等它读完再当场组批（约 130 毫秒），读取和组批仍然轮流进行。现在：
  - 预读比已组好的批次多读两页：一页留给下一批，另一页同时在读；
  - 请求拿走预读的行时，预读立刻接着读，不等回复写完。
- **每张表少一次空的往返。** 变更日志的基线结束不读源数据，原来却单独算一步，最后一批组好时读取还没结束，不带 `complete`，手机要再请求一次空批。现在它和读完最后一页在同一步完成。

## 诊断

- 手表日志的 `Read-ahead` 中，`queued` 最多数到两页。
- 预读跟上之后，`Local changes sent` 的 `pack` 应只有几毫秒（发的是提前组好的批次），并出现 `Packed ahead`。

## 升级

1. 用 ADB 安装新的手机 APK：`adb install -r ticbox-phone-1.0.10-release-<commit>.apk`，数据保留。
2. 在本地桥接页更新手表上的 Local Bridge。

这次只改了手表的 Local Bridge。手机 App 和 Magisk 模块只是版本号跟着变了；手机 1.0.9 也能配合新的手表提前请求，模块不更新也不影响同步。

## 未在真机验证

- 实际的提速：按 1.0.9 的计时估算，data_point 每页约 0.45 秒，一次全量同步约 13–14 秒，取决于手表上两个线程争用 CPU 和存储的程度。
- 预读多读一页后，同时写本地账本的事务是否让组批或确认等得更久。
