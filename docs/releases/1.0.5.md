# TicBox 1.0.5

手机 App、手表 Local Bridge 和内置的 Magisk 模块统一为 1.0.5（versionCode 6）。

## 改进

- 健康数据同步每页最多 1024 行，原来是 128 行，同样的数据只需原来约八分之一的来回。1.0.3 的一次全量同步里，data_point 约 160 页，24.5 秒的传输时间大多花在每页一次的来回上（每页约 150 毫秒），而不是数据量本身。每页仍受 1 MiB 的单帧限制，行很大时一页会少于 1024 行。
- 换手机或导入数据后的第一次同步之后，增量同步不再每次都读遍整张健康数据表。1.0.4 及更早，第一次同步看到的会话（睡眠等）在之后一天内都算“有变化”，每次增量同步都要从最老的会话开始重新检查健康数据；手表上有几万行时，每次要多花十几秒。

## 修复

- 健康变更日志仍然无法读取状态，也无法开启：1.0.4 的修复无效，root 辅助进程读取那项全局设置时同样被系统拒绝，root 并不例外。现在辅助进程在创建系统 context 之前先打开一个内存数据库，这时进程里还没有 Application，SQLite 跳过这项设置，使用默认值。

## 诊断

- 手表日志 `Local changes sent` 和 `Read-ahead` 把耗时拆成读源数据、写本地账本和组装批次三部分，用来判断一页的时间花在哪里。读取方法见[健康数据 · 排查](../dev/health.md#6-排查)。

## 升级

1. 用 ADB 安装新的手机 APK：`adb install -r ticbox-phone-1.0.5-release-<commit>.apk`，数据保留。
2. 在本地桥接页更新手表上的 Local Bridge。每页多大由手表决定，旧版手机也能接收 1024 行的页。
3. 在“健康变更日志”页重新读取状态，再按需开启。开启后的下一次同步会把健康数据完整重发一次。

## 已知情况

- 升级前已经同步过的会话保持原来的记录：如果第一次同步发生在升级前一天之内，那一天剩下的时间里增量同步仍会读遍整张表，之后恢复正常。

## 未在真机验证

- 变更日志的状态读取、开启和同步中的消费。
- 1024 行一页在真实蓝牙连接上的耗时，以及手表组装、压缩更大一页所需的时间和内存。
- 第一次同步之后增量同步的耗时。
