# TicBox 1.0.9

手机 App、手表 Local Bridge 和内置的 Magisk 模块统一为 1.0.9（versionCode 10）。

## 改进

- **同步时手表上的几项工作同时进行。** 原来手表写出一页之后才开始读下一页的源数据，读完才处理下一个请求；全量同步时 data_point 每页约 0.7 秒，几乎都花在手表上。
  - 预读改在单独的线程上：读源数据、算指纹、写本地账本，与组批、压缩和发送同时进行。
  - 上一批还在路上时，手表就提前组好下一批。每张表最多保留 3 个未确认的批次：手机正在入库的、正在传输的和提前组好的。
  - 手表的本地账本改用 WAL，组批和发送不用等预读那一页的事务提交。
- **手机收到一批后立即请求下一批。** 手机先发出下一个请求，再把刚收到的这一批入库，入库和下一批的传输重叠。确认仍随下一个请求发出，不增加往返；入库失败时不用提前请求到的那一批，之后按顺序重发。协议细节见[本地桥接协议 §3.2.1](../spec/local-bridge.md#321-提前请求下一批)。
- **运动库一个读取窗口只启动一个 root 辅助进程。** 原来运动日志、两张运动表的每一页各启动一次，每次约 2 秒，没有新训练时一次同步也要多花约 6 秒。现在第一次读运动库时启动，之后的分页和日志读取都交给它，见[本地桥接协议 §5](../spec/local-bridge.md#5-root-运动采集)。它启动不了时，照旧每次启动一次性的辅助进程。

## 修复

- 本地桥接页安装和重启时的进度说明（如 “Sending to the watch and installing…”）缩进太多，没有和上面的进度条对齐；应用管理里受保护应用的说明也是。现在与上面的内容左对齐。

## 行为变化

- 手表的本地账本（`health-incremental.sqlite`）升到第 2 版，升级时保留已组好、未确认的批次，升级后照常重发和确认。把 Local Bridge 降回 1.0.8 或更早时，旧版本打不开新版本的账本，同步会失败。
- 手机计时页的 read 只计读出已经在路上的回复和发出下一个请求的时间；手表组批和传输的一部分与入库重叠，所以 transfer 比实际的蓝牙时间短。

## 诊断

手表日志（标签 `TicBoxHealthBridge`）：

- `Read-ahead` 改为每读一页一行，`queued` 是还不属于任何批次的待传行数（最多数到一页）；
- `Packed ahead`：提前组好了一批，带耗时；
- `Fitness helper started`、`Fitness helper unavailable`（带原因）、`Fitness helper ended`：运动库辅助进程的启动、不可用和中途退出；
- `Journal read through the fitness helper`：经它读运动日志，带耗时。

## 升级

1. 用 ADB 安装新的手机 APK：`adb install -r ticbox-phone-1.0.9-release-<commit>.apk`，数据保留。
2. 在本地桥接页更新手表上的 Local Bridge。

只更新其中一边时，手机按 1.0.8 的方式一页一页请求；手表仍在单独的线程上预读并提前组批，运动库也只启动一个辅助进程。Magisk 模块的代码没有变化，只是版本号跟着变了；模块页会提示更新，不更新不影响同步，更新需要重启手表。

## 未在真机验证

- 实际的提速：按 1.0.7 的计时估算，一次全量同步从约 23 秒降到 14 秒左右，取决于蓝牙速度和手表上两个线程争用 CPU 和存储的程度。
- 运动库辅助进程降到运动应用的 UID 后读分页（原来一次性的分页辅助进程一直以 root 读取），以及 su 经管道传帧时不混入别的输出。
- 读取窗口结束后辅助进程是否都退出了。
- 本地账本从第 1 版升级到第 2 版时正好有未确认的批次。
