# TicBox 1.0.6

手机 App、手表 Local Bridge 和内置的 Magisk 模块统一为 1.0.6（versionCode 7）。

## 改进

1.0.5 的测量表明，全量同步的瓶颈是手表 CPU，而不是蓝牙或来回次数：每 1024 行手表要忙约 2 秒，其中写本地账本约占六成，组装批次约占两成，而蓝牙实际只用了约 6.5 秒。这一版减少手表上每一行的工作量：

- 行指纹的算法和结果不变，算法照旧用 SHA-256，但不再为每行复制一份排序后的 JSON，不再每次重新获取摘要算法，也不再用 32 次字符串格式化转十六进制。结果逐字节相同，所以手表上已经存下的指纹继续有效，升级后不会重发。
- 写本地账本时，一页的旧记录用一次查询取出，插入使用预编译的语句；只对确实要发送或保存的行生成 JSON 文本；整页没变化的行只用一条语句标记。
- 组装批次时直接拼接已保存的行文本，不再逐行解析、重新序列化再测大小；回复和存档也不再各序列化一遍。
- 确认（ACK）按这一批最后一个修订号一次删除，不再把整批约 500 KB 的 JSON 重新解析一遍后逐行删除。
- 增量同步读取官方数据时，不再为了单帧大小逐行试序列化；单帧的上限由组装批次时检查。
- 开着健康变更日志时，每张表完整读取结束后不再启动 root 辅助进程重读一次日志窗口，一次全量同步约少 4 次、共约 8 秒。下一轮开始时本来就会核对日志位置，如果日志在此期间被截断或重建，就从那里重新完整读取。

## 诊断

- 计时页的 read 下新增 queued：请求在手表上等它预读下一页所用的时间。原来这段时间被算进了 transfer，看起来像蓝牙很慢。
- 手表日志的 `Local changes sent` 和 `Read-ahead` 新增 `hash`（算行指纹的时间），`Local changes sent` 还新增 `queued`。读取方法见[健康数据 · 排查](../dev/health.md#6-排查)。

## 升级

1. 用 ADB 安装新的手机 APK：`adb install -r ticbox-phone-1.0.6-release-<commit>.apk`，数据保留。
2. 在本地桥接页更新手表上的 Local Bridge。只更新一边也能同步；只有手机和手表都是 1.0.6 时，计时页才显示 queued。

## 未在真机验证

- 全量和增量同步在手表上实际快了多少。
- 升级时如果正好有一批没确认的行，它按旧的方式逐行确认，这条兼容路径没有专门的测试。
